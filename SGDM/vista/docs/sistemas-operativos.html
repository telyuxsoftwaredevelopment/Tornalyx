Objetivo y alcance del documento

Formalizar el estudio del entorno de sistemas operativos sobre el que se despliega la plataforma Tornalyx (SGDM), abarcando tanto el sistema operativo cliente (Windows 11) como el del servidor (AlmaLinux 8.10), el diseño de las cuentas de administración del servidor bajo el principio de mínimo privilegio y la construcción de la suite de scripts en Bash para la automatización de la administración del servidor.

1. Estudio comparativo entre SO cliente y servidor

1.1 Sistema operativo cliente: Windows 11

Utilizado por los usuarios finales para acceder a la plataforma mediante navegador web. Ventajas: interfaz gráfica intuitiva, compatibilidad universal con navegadores modernos y soporte nativo para WSL2 (Windows Subsystem for Linux), permitiendo emular el servidor de producción en local.

1.2 Sistema operativo servidor: AlmaLinux 8.10 (Cerulean Leopard)

Distribución de grado empresarial compatible binariamente 1:1 con Red Hat Enterprise Linux (RHEL). Ofrece 10 años de soporte de seguridad garantizado, bajo consumo de recursos, SELinux preactivado y administración modular vía DNF AppStream.

3. Scripts de gestión del servidor (Bash)

Suite completa de scripts automatizados para la administración segura del servidor. Viven en SGDM/scripts/ y comparten la biblioteca lib/comun.sh (mensajes, verificación de privilegios, confirmaciones y bitácora). Cada uno funciona por separado —para cron o para encadenarlos— y gestion.sh los centraliza en un menú. Toda operación que modifica el sistema queda registrada en /var/log/tornalyx/gestion.log con fecha, usuario real (SUDO_USER) y detalle.

3.1 crear_roles.sh — Creación masiva e idempotente de cuentas

#!/bin/bash
# Crea los usuarios y grupos del sistema definidos en el estudio de roles.
USUARIOS=(
"admin_tornalyx|1001|admin_tornalyx|wheel,apache|/bin/bash|/home/admin_tornalyx|Administrador del servidor"
"operador_web|1002|apache||/bin/bash|/home/operador_web|Operador de la aplicacion web"
"dev_tornalyx|1003|dev_tornalyx|apache|/bin/bash|/home/dev_tornalyx|Desarrollo y pruebas"
"backup_tornalyx|1004|backup_tornalyx||/sbin/nologin|/var/backups/tornalyx|Cuenta de servicio para respaldos"
)
GRUPOS_REQUERIDOS=(wheel apache)
# ... crea grupos con mismo GID que UID, asigna contraseñas expiradas con chage -d 0 y bloquea nologin.

Además de crear cuentas y grupos, el script instala /etc/sudoers.d/tornalyx con las reglas de mínimo privilegio (validándolo con visudo antes de dejarlo en su lugar) y admite --dry-run para ver qué haría sin tocar el sistema.

3.2 a 3.8 Scripts auxiliares y Menú Principal gestion.sh

  • gestion.sh: Menú principal que centraliza todas las operaciones de mantenimiento, más un modo doctor que diagnostica el entorno completo (sintaxis de los scripts, cuentas, permisos, herramientas, tareas programadas —incluida la antigüedad del último respaldo— y servicios).
  • usuarios.sh / grupos.sh: Altas, bajas y modificaciones interactivas de cuentas y grupos. Las cuentas del sistema (UID < 1000) y los grupos root, wheel y apache están protegidos contra borrado.
  • registrar_grupo.sh: Asignación y desvinculación de usuarios a grupos secundarios con usermod -aG y gpasswd -d.
  • listar.sh: Consultas seguras parseando /etc/passwd y /etc/group con cut. Es el único que no requiere privilegios.
  • servicios.sh: Control de servicios de sistema (Apache, MySQL, firewall) mediante systemctl, resolviendo el nombre real de cada unidad (httpd/apache2, mysqld/mariadb). Antes de reiniciar o recargar Apache valida su configuración, y probar comprueba de punta a punta que el sitio y el API respondan.
  • permisos.sh: Gestión de propiedad y permisos octales sobre el árbol del proyecto en /var/www/tornalyx (directorios 750, archivos 640, rutas escribibles 2770), contextos de SELinux y auditoría con verificar, que además comprueba que ninguna capa del MVC ni ninguna vista .html haya quedado dentro del DocumentRoot (SGDM/publico).

3.9 a 3.11 Operación de la aplicación y de la base de datos

  • desplegar.sh: Despliegue completo —git pull, migraciones pendientes, permisos, recarga de Apache y verificación posterior— o por partes (solo-migrar, solo-codigo, estado). Aplica los add_*.sql con el mismo criterio que el migrador PHP: registra cada uno en schema_migrations e ignora únicamente los errores que significan "ya estaba hecho".
  • respaldo.sh: Respaldo de la base (mysqldump --single-transaction) y de los archivos de usuario, con checksum SHA-256, verificación de integridad del volcado, rotación por antigüedad y restauración con confirmación y copia previa del estado actual.
  • monitoreo_bd.sh: Informe del estado de la base (versión, conexiones, tamaño de tablas, consultas lentas, disco) y un modo alerta silencioso para cron, que devuelve 0 sin problemas, 1 ante umbrales superados o falta de respaldos, y 2 si la base no responde.
  • cron.sh: Instala las tareas programadas en /etc/cron.d/tornalyx —respaldo completo diario a las 03:15 con la cuenta backup_tornalyx, control de la base cada 15 minutos y auditoría de permisos los domingos— junto con la rotación semanal de sus registros en /etc/logrotate.d/tornalyx. Se eligió /etc/cron.d sobre el crontab personal porque declara el usuario de cada tarea en el propio archivo y permite revisarlo, versionarlo y quitarlo sin editar el spool de ninguna cuenta. Su acción probar ejecuta una tarea con el entorno pelado que le da cron (env -i), que es la única manera de detectar una credencial faltante antes de que el respaldo falle en silencio durante semanas.

Cada uno usa el usuario de base de datos que le corresponde según dcl.sql (tornalyx_ddl para migrar, tornalyx_backup —solo lectura— para volcar y tornalyx_monitor para consultar estado), nunca el de la aplicación: tornalyx_dml no debe poder tocar el esquema ni leer un respaldo completo. Las credenciales se resuelven en tres niveles, de mayor a menor prioridad: el entorno de quien ejecuta el script, el archivo /etc/tornalyx/credenciales.env (600 root:root, el que hace posible el cron, ya que una tarea programada arranca sin nadie que exporte variables) y, como último recurso, el .env de la aplicación únicamente para el host, el puerto y el nombre de la base.
